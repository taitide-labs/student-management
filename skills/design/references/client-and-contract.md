# 客户端与契约设计

## 前置流程

向用户确认需要支持的客户端、风格或参照物。

## 执行流程

1. 编写 `DESIGN.md` 初稿。
2. 完成 Walking Skeleton，并选择使用工具完成自检，按需使用视觉能力验证。
3. 让用户审查 Walking Skeleton，直到通过。
4. 编写或生成契约初稿。
5. 拆分任务，编写功能验收测试。
6. 并行开发。
7. 编写 E2E 测试。
8. 让用户审查，直到全部通过。
9. 冻结 `DESIGN.md`、契约、验收与 E2E 测试。

### 新增页面需求

- 遵循 Keystone Interface 将新路由或入口标记为 `Planned`（仅开发与测试环境可达，生产构建屏蔽）后合入 `main`，确保主干随时可 Hotfix 且不暴露未联调页面。

### 变更页面需求

- 遵循 Branch by Abstraction 将新版视图或模块作为独立实现合入 `main`（既有生产挂载点继续指向旧实现，避免在旧代码内散落条件开关），留待末尾整体验收切换并清理旧实现。
- 若处理的增量或变更需求时，先补充上下文，直接从步骤 4 开始。
- 变更需求比增量需求多一步：为旧功能添加注释。

> [!WARNING]
> 视觉能力应当在首次或 UI 变化时按需使用，不可滥用，避免消耗过多 Token。

## 核心原则

- 功能、视觉、组件分层
- 多客户端情况下，优先 CLI > Web > Desktop 测试逻辑。

## 架构

采用 Feature-Sliced Design 理念，但不采用其过重的结构划分。

## 契约分类

按通信边界划分：

- 同语言进程内：纯声明 contracts crate，例如 CLI。
- 跨语言进程内：使用 Rust `#[napi]` 契约壳 或 `.wit`，例如 TS ↔ Rust（NAPI / WASM）。
- 本机跨进程 IPC：使用 `tauri-specta` 或 `.proto over UDS/stdio`，例如 Tauri / Electron / CLI ↔ Daemon。
- 跨网络：`.proto` 或 `.tsp`

## 契约规则

- 契约遵循 SSOT
- 遵循 RFC 9457
- 遵守 Parallel Change 向后兼容原则
